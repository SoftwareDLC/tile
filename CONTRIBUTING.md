# Contributing

Thanks for helping improve TILE.

## Contribution Model

TILE uses a lightweight trunk-based model:

- `main` is the only long-lived development branch and should always be releasable.
- Contributors should work from forks or short-lived branches named by intent, such as `fix/escaping`, `feat/first-class-delimiter`, or `docs/benchmarks`.
- Pull requests are the unit of review. Avoid direct pushes to `main` except for repository administration.
- Release history is represented by immutable git tags, such as `v0.1.0`, that match the npm package version.
- We do not use a permanent `develop` branch. If a larger release needs stabilization, maintainers may temporarily create a `release/<version>` branch and delete it after publishing.

Recommended GitHub branch protection for `main`:

- Require pull requests before merging.
- Require the CI check to pass.
- Require at least one approving review.
- Require conversation resolution before merging.
- Require branches to be up to date before merging when GitHub reports stale checks.
- Restrict force pushes and branch deletion.

## Local Setup

```sh
pnpm install
pnpm check
```

## Issues

Use issues for bugs, feature proposals, benchmark questions, and documentation gaps.

- For bugs, include the input JSON or a minimal reproducible example.
- For encoding changes, state whether the change affects lossless `encodeJsonToTile` output, first-class projection output, or both.
- For benchmark changes, describe the fixture, question family, and why the question should favor a specific TILE projection.

## Pull Requests

- Keep changes focused and include tests for behavior changes.
- Preserve round-trip compatibility for existing TILE versions unless a breaking change is intentional and documented.
- Add or update benchmark fixtures/results when changing projection behavior or benchmark claims.
- Update README/docs when changing public API, delimiters, benchmark interpretation, or LLM harness behavior.
- Run `pnpm check` before opening a pull request.

PRs should generally be squash-merged unless maintainers intentionally preserve a multi-commit history for a larger change.

## Releases

This package is intended to be published from the `dist` output generated by `pnpm build`.

Release boundary:

- Automated assistants and local coding agents must never run commands that publish packages, push git commits/tags, create GitHub releases, or otherwise mutate external registries/remotes.
- Assistants may prepare release artifacts, run verification, inspect dry-run package contents, and provide the exact commands for a maintainer to run.
- A human maintainer runs all `git push`, `npm publish`, `twine upload`, GitHub release, PyPI, and npm registry commands.

Preparation process:

1. Confirm `main` is green in CI.
2. Run `pnpm check`.
3. Run `pnpm test:python` when the Python package or shared conformance cases changed.
4. Build and check the Python distributions from `packages/python` when preparing a PyPI release.
5. Run `npm --cache .npm-cache pack --dry-run --json` and inspect the package contents.
6. Update package versions using semver.
7. Prepare release notes that summarize API changes, benchmark changes, package changes, and migration notes.

Maintainer publish commands:

```sh
git push origin main
git push origin v<version>
npm publish --access public
cd packages/python
python -m build
python -m twine check dist/*
python -m twine upload dist/*
```

Only run the commands that match the release being published. For local RTK shells, prefix shell commands with `rtk`.

Versioning policy:

- Patch: bug fixes, docs, benchmark updates, and non-breaking internals.
- Minor: new APIs, new encoder options, new first-class projection capabilities, or new supported TILE versions that remain backward compatible.
- Major: breaking API changes or intentionally incompatible TILE format changes.
